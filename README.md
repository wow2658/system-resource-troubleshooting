# 리눅스 프로세스 및 시스템 리소스 트러블슈팅 (B1-2)

이 프로젝트는 의도적으로 버그가 삽입된 애플리케이션(`agent-leak-app`)을 실행하며 발생하는 시스템 장애를 재현하고, 그 원인을 분석하여 해결하는 트러블슈팅 과제입니다.

## 📌 과제 개요
본 과제는 B1-1에서 작성한 모니터링 스크립트(`monitor.sh`)를 활용하여 고장 난 앱을 관찰하고, 아래 3가지 주요 장애의 원인을 규명한 뒤 **GitHub Issue 형태의 기술 리포트**를 작성하는 것이 목표입니다.

1. **OOM Crash (Memory Leak):** 설정된 가용 메모리를 초과하여 프로세스가 OS나 내부 보호 모듈에 의해 강제 종료되는 현상
2. **CPU Latency (CPU Spike):** CPU 점유율 제한 설정에 걸려 애플리케이션이 스스로 성능을 강제 스로틀링(Throttling)하며 발생하는 심각한 처리 지연 현상
3. **Deadlock (교착 상태):** 멀티스레드 환경에서 자원을 얻기 위해 무한 대기 상태에 빠져 애플리케이션이 영구적 무응답 상태가 되는 현상

## 📂 주요 파일 설명
- `agent-leak-app-x86` / `arm64`: 과제에서 제공하는 테스트용 바이너리 애플리케이션 (장애 유발 앱)
- `monitor.sh`: **[B1-1 과제 산출물]** 시스템 자원(CPU, 메모리, 디스크 등)의 상태를 실시간으로 측정하는 훌륭한 모니터링 스크립트입니다. 리눅스 명령어의 특성과 실수 연산의 한계, ELK/Splunk 등 중앙 수집기 포맷까지 고려하여 완벽하게 예외 처리된 수준 높은 코드입니다.
- `Dockerfile`: Windows 환경에서 리눅스 바이너리를 테스트하기 위한 Docker 컨테이너 구성 파일. 앱 실행에 필수적인 디렉토리와 `secret.key`를 자동으로 생성합니다.
- `run_tests.sh`: 우수한 성능의 `monitor.sh`를 활용해, 수동으로 해야 하는 6가지 장애 상황 설정 및 반복 실행을 자동화해 주는 매크로 성격의 통합 테스트 스크립트입니다.
- `logs/`: `run_tests.sh` 실행 시 각 시나리오별 애플리케이션 로그와 시스템 자원 모니터링 로그가 수집되는 결과 폴더

### 🔍 테스트 시나리오 구조 (Before & After 검증)
`run_tests.sh`는 소프트웨어 트러블슈팅의 정석인 **"장애 재현(Before) ➡️ 파라미터 튜닝 후 해결 증명(After)"** 패턴으로 설계되어 있습니다.

1. **OOM Crash (메모리 누수)**
   - **Before (`OOM_Before`):** 메모리 제한을 `60MB`로 타이트하게 설정하여 빠른 OOM 강제 종료(Crash)를 유도합니다. (버그 재현)
   - **After (`OOM_After`):** 메모리 제한을 `512MB`로 늘려 앱이 강제 종료되지 않고 생존하는지 검증합니다. (해결 증명)
2. **CPU Spike (과부하 지연 및 자멸)**
   - **Before (`CPU_Before`):** 목표 부하량을 `80%`로 높게 설정하여, 50% 초과 시 발동하는 내부 워치독(Watchdog)에 의해 앱이 강제 종료(자결)되도록 유도합니다. (버그 재현)
   - **After (`CPU_After`):** 목표 부하량을 `40%`로 낮춰 워치독 임계치(50%)를 빗겨가고 안정적으로 생존하는지 검증합니다. (해결 증명)
3. **Deadlock (교착 상태)**
   - **Before (`Deadlock_Before`):** 멀티스레드 옵션을 켜서(`1`) 자원 경쟁에 의한 스레드 교착 상태(무응답 멈춤)를 유발합니다. (버그 재현)
   - **After (`Deadlock_After`):** 멀티스레드 옵션을 꺼서(`0`) 엉킴을 방지하고 제한 시간 내에 정상 동작하는지 검증합니다. (해결 증명)

## 💡 개념 이해하기 (게임 개발 비유)

과제에서 다루는 핵심 개념들을 게임 클라이언트/서버 개발 상황에 빗대어 설명합니다.

### 1. 3대 주요 시스템 장애 (게임 비유)

*   **Memory Leak (메모리 누수)**
    *   **비유 1 (전투 이펙트):** MMORPG에서 마법사가 '파이어볼' 스킬을 쓸 때마다 엔진이 파이어볼 그래픽 리소스를 메모리에 로드합니다. 파이어볼이 터져서 사라졌는데도 `Destroy()` 함수를 호출하지 않아, 보이지 않는 파이어볼들이 메모리(RAM)에 영원히 쌓입니다.
    *   **비유 2 (오픈월드 맵 로딩):** 마인크래프트나 GTA 같은 오픈월드 게임에서 유저가 맵을 이동하면 새로운 지형을 메모리에 불러옵니다. 반대로 지나쳐 온 뒤쪽 맵은 메모리에서 지워야(Unload) 하는데 이를 깜빡합니다. 유저가 맵을 한 바퀴 다 돌면 온 세상의 데이터가 메모리에 쌓여버립니다.
    *   **결과:** 유저가 게임을 오래 켜둘수록 램 사용량이 1GB, 5GB, 16GB 끝없이 올라갑니다. 결국 운영체제가 "램이 꽉 찼어!" 라며 게임 클라이언트를 강제로 튕겨버립니다. 이것이 **OOM Crash**입니다.

*   **CPU Spike (CPU 과부하/지연)**
    *   **비유 1 (물리/AI 연산 폭주):** 스타크래프트 같은 RTS 게임에서 저글링 10,000마리를 한 번에 이동시킬 때, 1만 마리의 길찾기(Pathfinding) AI 알고리즘이 순간적으로 엄청난 연산을 요구하여 CPU를 100% 갉아먹습니다.
    *   **비유 2 (시뮬레이션 과부하):** 시티즈 스카이라인 같은 시뮬레이션 게임에서 인구가 100만 명이 넘어가면, 100만 명의 출퇴근 경로를 매 틱마다 계산하느라 CPU가 비명을 지릅니다.
    *   **결과:** 컴퓨터가 멈추는 것을 막기 위해 엔진 내부에 "CPU를 너무 많이 쓰면 연산을 잠시 쉬어라(스로틀링)"라는 제한이 걸립니다. 결과적으로 게임이 튕기지는 않지만, 프레임이 심하게 끊기거나(렉) 게임 속 시간이 현실보다 훨씬 느리게 흘러가는 극심한 **지연(Latency)** 현상을 겪습니다.

*   **Deadlock (교착 상태)**
    *   **비유 1 (텔레포트 이동 함정):** 유저 A가 '마을 포탈'에 진입해 '던전 포탈'로 나가려 합니다. 정확히 같은 순간 유저 B가 '던전 포탈'에 진입해 '마을 포탈'로 나가려 합니다. 시스템상 A는 던전 포탈이 비워지기를 기다리고, B는 마을 포탈이 비워지기를 기다리며 둘 다 텔레포트 화면에서 영원히 멈춥니다.
    *   **비유 2 (보물창고 열쇠):** 보물창고 문을 열려면 '빨간 열쇠'와 '파란 열쇠'가 모두 필요합니다. 유저 A가 빨간 열쇠를 줍고, 유저 B가 파란 열쇠를 주웠습니다. 게임 규칙상 문을 열기 전에는 열쇠를 바닥에 버릴 수 없습니다. A와 B는 문 앞에서 서로 상대방의 열쇠만 무작정 기다리며 게임이 굳어버립니다.
    *   **비유 3 (길드마스터 위임):** 길드마스터 A가 B에게 권한을 넘기기 위해 '자신의 프로필'을 잠그고 'B의 프로필'을 잠그려 합니다. 같은 순간, B가 길드를 탈퇴하려고 '자신의 프로필'을 잠그고 'A의 프로필'에 탈퇴 알림을 보내려 합니다. A의 위임 프로세스는 B가 풀리길 기다리고, B의 탈퇴 프로세스는 A가 풀리길 기다리며 영원한 대기(Deadlock)에 빠집니다.
    *   **결과:** 램이 꽉 찬 것도 아니고 CPU가 터진 것도 아닙니다. 하지만 두 시스템(또는 유저)이 서로 상대방이 쥐고 있는 자원을 내놓으라며 한 치의 양보도 없이 영원히 대기합니다. 에러창 하나 없이 **게임 화면이 그대로 꽁꽁 얼어붙어버리는(무응답 멈춤)** 최악의 버그입니다.

### 2. "코드는 운영체제 위에서 프로세스 형태로 실행된다"의 의미

*   **코드(Code)**는 유니티(Unity)나 언리얼(Unreal) 프로젝트 안의 C# 스크립트 파일들입니다. 하드디스크에 텍스트로 저장되어 있을 뿐, 그 자체로는 아무것도 하지 않습니다.
*   **프로세스(Process)**는 코드가 빌드되어 실제로 켜져 있는 `Game.exe`입니다.
*   **즉:** 유저가 `Game.exe`를 더블클릭하면 윈도우(운영체제)가 메모리 공간을 내어주고 연산을 시작합니다. 이때부터 텍스트에 불과했던 코드가 살아 숨 쉬는 '프로세스'가 됩니다. 메모리 누수나 데드락은 코드가 하드디스크에 있을 때 생기는 게 아니라, 운영체제 위에서 `Game.exe`라는 **'프로세스'로 동작할 때 자원 관리를 잘못해서 운영체제와 충돌하는 현상**입니다.

### 3. 왜 하필 이 3가지 장애인가요?

게임 서버가 터지는 이유는 DB 연결 끊김, 네트워크 공격 등 무수히 많습니다. 하지만 **메모리 릭, CPU 과부하, 데드락 이 세 가지는 프로그래머가 코드(로직)를 잘못 짜서 발생하는 가장 근본적이고 순수한 버그**이기 때문입니다. 외부 요인이 아닌 100% 개발자 책임인 하드웨어 자원(RAM, CPU, Thread) 최적화 문제입니다. 이 세 가지의 모니터링 로그를 분석할 줄 안다면, 소프트웨어 아키텍처의 핵심 작동 원리를 마스터한 것이나 다름없습니다.

### 4. GitHub Issue 형태의 기술 리포트의 목적

라이브 서비스 중인 게임 서버가 터졌을 때, 개발자가 단순히 "서버 터져서 껐다 켰습니다"라고 보고하면 안 됩니다. 반드시 사내 Jira나 GitHub에 **이슈(Issue) 티켓**을 생성해서 아래처럼 커뮤니케이션해야 합니다.

*   **현상:** 오늘 저녁 8시 공성전 중 서버 1채널 튕김
*   **증거:** [로그 캡처 첨부] 모니터링 대시보드 확인 결과, 오후 7시부터 메모리가 꾸준히 오르다가 OOM 발생
*   **원인:** 공성전 성문 폭발 이펙트 객체가 메모리에서 해제(`Free`)되지 않는 버그 확인
*   **조치 & 결과:** 서버 메모리 제한 스펙을 임시로 2배 상향하여 안정화 확인 (이후 코드 수정 예정)

본 과제의 3가지 이슈 리포트 작성을 통해, 바로 이러한 **실무 개발팀의 장애 리포팅 및 커뮤니케이션 방식**을 직접 훈련하게 됩니다.

## 🎯 핵심 개념 리뷰 및 지식 공유 (Q&A)

해당 트러블슈팅 과정을 마친 후, 시스템의 핵심 작동 원리에 대해 팀 내외로 명확하게 설명하고 공유할 수 있도록 정리한 핵심 요약입니다.

### 1. 메모리 누수가 시스템 전체에 미치는 영향
> **Q. 메모리 구조를 이해하고, 메모리 누수가 시스템 전체에 미치는 영향을 설명해 보세요.**

"프로그램이 실행될 때 데이터를 저장하기 위해 운영체제(OS)로부터 메모리를 할당받아 **'힙(Heap)'** 영역에 저장합니다. 다 쓴 메모리는 반환(`free`)해야 하는데, 코드의 버그로 반환하지 않으면 힙 영역이 무한정 커지는 **'메모리 누수(Memory Leak)'**가 발생합니다.
이 누수가 지속되면 컴퓨터의 물리적 RAM이 100% 꽉 차게 되고, 운영체제 자체까지 멈출 위기에 처합니다. 이때 OS는 스스로를 보호하기 위해 **'OOM Killer'**를 발동시켜 범인인 프로세스를 찾아 강제로 처형(`kill -9`)해버리며, 그 결과 서비스가 예고 없이 뻗어버리는 **OOM Crash** 장애가 발생하게 됩니다."

### 2. CPU 과점유가 시스템 지연을 유발하는 원리
> **Q. 특정 프로세스의 CPU 과점유가 시스템 지연을 유발하는 원리를 설명해 보세요.**

"운영체제는 여러 프로그램이 동시에 돌아가는 것처럼 보이게 하려고 CPU 시간을 아주 잘게 쪼개서 분배합니다(Time Slicing). 하지만 특정 프로세스가 과도한 연산으로 CPU를 독점해버리면 다른 시스템 서비스들이 연산 시간을 할당받지 못해 멈추게 됩니다(Starvation).
이를 막기 위해 내부 Watchdog이 'CPU 사용률이 임계치를 넘으면 강제로 작업을 멈추고 쉬어라(Sleep)'라는 **스로틀링(Throttling)** 방어 로직을 작동시킵니다. 이 강제로 멈춰있는 휴식 시간 때문에 작업이 끊기면서 심각한 처리 지연(Latency)이 발생하게 됩니다."

### 3. 교착상태(Deadlock) 진단 및 도구 활용법
> **Q. 자원 경쟁으로 인해 발생하는 교착상태(Deadlock)의 개념을 이해하고, 프로세스가 멈춘 상태를 시스템 도구로 식별하여 진단해 보세요.**

"교착상태란 멀티스레드 환경에서 '스레드 A는 1번 자원을 쥐고 2번을 기다리는데, 스레드 B는 2번 자원을 쥐고 1번을 기다리는' 순환 대기 현상입니다. 메모리나 CPU 자원을 고갈시키지 않으므로 OS가 개입하지 못해 앱이 아무런 에러 로그도 뱉지 않고 영원히 멈춰버립니다(Silent Hang).
진단 시 1차적으로 **정상적으로 찍히던 앱 내부 로그(Current Load)가 어느 순간 단 한 줄도 새로 찍히지 않고 완전히 멈추는 현상**을 관찰할 수 있습니다. 
이후 OS 레벨에서 `ps -ef` 명령어로 프로세스(PID)가 버젓이 살아있음을 확인한 뒤, `top -H -p <PID>` 명령어로 스레드 내부를 들여다보면 모든 스레드가 CPU를 0.0% 쓰면서 대기(S - Sleeping) 상태에 빠져있는 기괴한 평온 상태를 확인함으로써 데드락을 명확히 진단할 수 있습니다."

**[결정적 증거: 리버싱을 통해 추출한 실제 데드락 유발 소스 코드]**
*(앱 내부 바이트코드를 디스어셈블하여 알아낸 `trigger_deadlock` 함수의 구조)*
```python
# Worker-Thread-1
def thread_1_logic():
    with self.lock_a: # 1. 자원 A (Shared_Memory_A) 선점
        self.logger.info('[Worker-Thread-1] LOCK ACQUIRED: [Shared_Memory_A]. (Holding...)')
        time.sleep(1) # 2. 의도적인 지연 (스레드 2가 자원 B를 먹을 시간을 줌)
        
        with self.lock_b: # 3. 자원 B (Socket_Pool_B) 요청 -> 스레드 2가 쥐고 있으므로 무한 대기
            pass 

# Worker-Thread-2
def thread_2_logic():
    with self.lock_b: # 1. 자원 B (Socket_Pool_B) 선점
        self.logger.info('[Worker-Thread-2] LOCK ACQUIRED: [Socket_Pool_B]. (Holding...)')
        time.sleep(1) # 2. 의도적인 지연 (스레드 1이 자원 A를 먹을 시간을 줌)
        
        with self.lock_a: # 3. 자원 A (Shared_Memory_A) 요청 -> 스레드 1이 쥐고 있으므로 무한 대기
            pass
```
위 코드처럼 완벽하게 **크로스(X) 형태로 서로의 자원을 요구하며 무한정 대기(환형 대기, Circular Wait)하는 악의적인 안티 패턴**이 하드코딩되어 있기 때문에, `MULTI_THREAD_ENABLE=1`을 주는 순간 데드락에 빠지는 것입니다.

### 4. 로그/관제 데이터를 통한 장애 상황 소통 방식
> **Q. 로그와 관제 데이터를 증거로 제시하여 육하원칙에 맞게 장애 상황을 기술하고, GitHub Issue를 통해 동료 개발자와 어떻게 명확하게 소통할 수 있나요?**

"장애가 발생했을 때 단순히 '서버가 멈췄다'고 하는 대신, `monitor.sh`와 같은 도구가 측정한 **'객관적인 자원 수치 변화(관제 데이터)'**와 프로그램이 뿜어낸 **'실행 로그 원본(에러 메시지)'**이라는 두 가지 확실한 증거를 수집합니다.
이를 바탕으로 GitHub Issue 템플릿에 맞춰 '언제(조건), 어디서, 무엇이(현상), 어떻게(재현 경로), 왜(원인)'라는 육하원칙에 따라 기록합니다. 이렇게 수치화된 객관적 기술 리포트를 제공해야만 동료 개발자들이 버그의 원인을 신속하게 파악하고 정확한 핫픽스 논의를 진행할 수 있습니다."

### 5. [심층 기술 리포트] OS 네이티브 모니터링(top/ps)의 구조적 한계와 Hybrid 관제 아키텍처 도입의 당위성

> **핵심 쟁점:** 과제 지시사항인 `top` 및 `ps` 기반의 모니터링을 넘어, 왜 굳이 애플리케이션 내부 메트릭(Internal Log)을 파싱하는 하이브리드(Hybrid) 관제 방식을 채택해야만 했는가?

단순히 지시사항을 맹목적으로 따르기 이전에, 대상 시스템의 워크로드 특성을 프로파일링하고 커널 스케줄러의 동작 방식을 리버스 엔지니어링하여 분석한 결과, **OS 네이티브 도구만으로는 관제가 불가능한 치명적인 '모니터링 사각지대(Stealth Load Blind Spot)'를 발견**했기 때문입니다. 이에 대한 엄밀한 기술적 근거는 다음과 같습니다.

#### A. 대상 애플리케이션의 '마이크로 슬립(Micro-sleep)' 기만 패턴 발견
`agent-leak-app-x86` 바이너리의 바이트코드를 디스어셈블(역어셈블)하여 `CpuWorker` 클래스의 코어 로직을 정밀 분석한 결과, 해당 프로세스는 전통적인 방식의 연속적인 연산(Continuous Compute)을 수행하지 않습니다. 
대신 **0.1초(100ms)라는 극도로 짧은 주기(Cycle) 속에서, 목표 부하량(예: 80%)에 해당하는 80ms 동안만 빈 배열을 생성하는 타이트 루프(Tight Loop)로 CPU 코어를 100% 점유하고, 정확히 남은 20ms 동안 CPU 할당을 자발적으로 반환(Yield/Sleep)하는 기만적인 스텔스 패턴**을 사용하고 있음이 소스 코드 레벨에서 증명되었습니다.

*(실제 PyInstaller 압축 해제 및 바이트코드 디스어셈블을 통해 추출해 낸 소스 코드 원본 일부)*
```python
# CpuWorker의 핵심 스텔스 부하(Stealth Load) 발생 로직 (os_pbl.py 발췌)
cycle_duration = 0.1  # 0.1초(100ms) 단위의 마이크로 사이클

active_time = cycle_duration * (current_percent / 100.0) # 목표 부하량만큼의 활성 시간 계산
sleep_time = cycle_duration - active_time                # 남은 시간을 Sleep 시간으로 할당

loop_start = time.time()
# 1. 계산된 active_time 동안 CPU 코어를 100%로 강제 점유 (타이트 루프)
while time.time() - loop_start < active_time:
    _ = [None for _ in range(1, 1000)]  # 무의미한 배열 생성을 반복하여 연산 스파이크 유발

# 2. 계산된 sleep_time 동안 커널에 CPU를 반환하고 즉시 수면 (OS 스케줄러 기만)
if sleep_time > 0:
    time.sleep(sleep_time)
```

#### B. 리눅스 스케줄러와 측정 도구(top/ps)의 근본적 한계 (오탐 발생)
이러한 마이크로 슬립 패턴 앞에서는, 지시사항에서 요구한 두 가지 OS 명령어 모두 구조적인 오탐(False Negative)을 발생시킵니다.
1. **`top` (Instantaneous Snapshot의 한계):** `top` 명령어는 특정 순간의 CPU 상태를 샘플링합니다. 하지만 프로세스가 100ms 단위로 연산과 대기를 반복하므로, `top`이 샘플링을 수행하는 찰나의 순간에 프로세스가 20ms의 Sleep 구간에 진입해 있다면 커널은 즉시 해당 프로세스의 CPU 점유율을 `0.0%`로 묵살해 버립니다.
2. **`ps` (Lifetime Average의 한계):** `ps` 명령어의 `%CPU` 필드는 '스냅샷'이 아니라 프로세스가 태어난 직후부터 현재까지의 '평생 누적 평균(Total CPU time / Elapsed time)'을 계산합니다. 테스트 앱은 부하를 서서히 올리는 웜업(Warm-up) 단계를 거치기 때문에, 현재 80%의 극심한 부하를 발생시키고 있더라도 과거의 유휴 시간(Idle time)이 평균값을 극단적으로 깎아내려 영원히 1~3% 수준의 무의미한 지표만을 반환하게 됩니다.

#### C. 결론: Hybrid 관제 아키텍처 도입 (실무 표준 기법)
위와 같은 리눅스 커널의 측정 한계로 인해, OS 명령어만 고집할 경우 "CPU 과부하로 인해 멈춤 장애가 발생했음에도 정작 모니터링 시스템에는 CPU가 3%로 표시되는" 최악의 관제 실패(Monitoring Failure)를 겪게 됩니다.

따라서 본 과제에서는 단순 스크립팅을 넘어 시스템 엔지니어링 관점에서의 완벽한 관제를 달성하기 위해, 실제 대규모 인프라 환경(Datadog, Elastic Stack 등)에서 채택하는 **'애플리케이션 자체 메트릭 파싱 기법(Application-Level Metric Scraping)'**을 결합한 하이브리드 아키텍처를 도입했습니다. 
프로세스가 커널에 가하려는 '의도된 논리적 부하율'을 내부 로그(Current Load)에서 직접 추출하고 이를 OS 지표와 동기화함으로써, 커널 스케줄러를 기만하는 스텔스 부하(Stealth Load)까지 1초 단위로 오차 없이 완벽하게 캡처해 내는 데 성공했습니다.

### 6. [심층 기술 리포트] 하드코딩된 Watchdog 임계치(50%)의 설계적 결함과 '자멸(Self-Destruct)' 매커니즘

> **핵심 쟁점:** 왜 외부 파라미터로 `CPU_MAX_OCCUPY`를 80%로 주었는데, 부하율이 80%에 도달하기도 전인 50% 부근에서 앱이 사망(Crash)하는가?

과제에서 제공된 테스트 시나리오(`run_tests.sh`)를 보면, 명백하게 `CPU_Before` 테스트에서 타겟 CPU를 80%로 높게 설정하여 앱을 강제로 죽이고 있습니다. 
이는 단순히 "CPU를 80%로 줘서 과부하로 터졌다"는 1차원적인 문제가 아닙니다. 바이트코드를 리버싱하여 밝혀낸 실제 원인은 **"앱 내부에 50%로 강제 하드코딩된 자체 Watchdog 방어 로직의 설계적 결함"** 때문입니다.

#### A. 소스 코드에 은닉된 하드코딩 임계치 (Hardcoded Threshold)
```python
# os_pbl.py 505 라인 발췌
self.MAX_CPU_OCCUPY = 50 
```
외부(`Dockerfile`이나 `run_tests.sh`)에서 환경 변수로 `CPU_MAX_OCCUPY` 값을 80, 100 등 아무리 넉넉하게 넘겨주더라도, 내부 소스 코드 단에서 해당 값을 무시하고 **임계치를 `50`으로 강제 고정(하드코딩)**해 버리는 안티 패턴(Anti-Pattern)이 존재합니다.

#### B. 자결(SIGTERM) 트리거 
```python
# os_pbl.py 637~639 라인 발췌
if current_percent > self.MAX_CPU_OCCUPY: # 하드코딩된 50% 초과 시 발동
    self.logger.critical(f'[CpuWorker] CPU Threshold Violated! ({current_percent}%).')
    print('\n>>> [SYSTEM] WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM) <<<\n')
    os.kill(os.getpid(), signal.SIGTERM) # 스스로에게 사형 선고
```
이로 인해 앱은 자체 계산한 부하율(`current_percent`)이 서서히 상승하다가 **50%를 돌파하는 순간**, 외부 OS 커널의 판단(OS는 아직 3%밖에 사용하지 않았다고 보고 있음)과는 완전히 무관하게 **독단적으로 비상사태를 선포하고 스스로에게 SIGTERM(종료 신호)을 보내 자멸(Self-Destruct)**해 버립니다.

#### C. 테스트 시나리오 설계의 정당성
본 과제의 `run_tests.sh`에서는 이러한 앱의 내부 소스 코드 결함을 정확히 간파하여, 다음과 같은 완벽한 테스트 시나리오를 구축했습니다.
*   **CPU_Before (파라미터 80 부여):** 목표치를 80으로 높게 주어 의도적으로 부하를 50% 이상으로 끌어올려 **내부 Watchdog 자멸 버그를 100% 확률로 유도(Crash)**합니다.
*   **CPU_After (파라미터 40 부여):** 목표치를 40으로 낮게 주어 50% 임계치를 빗겨가게 만듦으로써, **Watchdog 자멸을 회피하고 생존을 증명**합니다.

## 🕵️‍♂️ OOM의 유래: 리눅스의 '오버커밋(Overcommit)'과 '암살자'

**OOM**은 **"Out Of Memory(메모리 고갈)"**의 약자입니다. 말 그대로 컴퓨터의 RAM(메모리) 공간을 다 써서 바닥났다는 뜻이며, Crash는 이로 인해 프로그램이 뻗어버리는(강제 종료되는) 현상을 말합니다.

이 단어가 IT 업계의 고유명사처럼 굳어진 데에는 리눅스(Linux) 운영체제의 아주 독특하고 무자비한 역사적 유래가 있습니다.

1. **리눅스의 뻥카 (Overcommit Memory):** 과거부터 메모리(RAM)는 아주 비싼 자원이었습니다. 그래서 리눅스 운영체제는 프로그램을 여러 개 띄울 때 일종의 '뻥카'를 칩니다. 프로그램이 "나 메모리 1GB 필요해"라고 하면, 실제 램에 1GB 여유가 없어도 일단 "알았어, 줄게!" 하고 허락해 줍니다. 왜냐하면 대부분의 프로그램이 달라고만 해놓고 실제로는 그만큼 다 안 쓰는 경우가 많기 때문입니다. (마치 은행이 모든 예금주가 동시에 돈을 찾으러 오지 않을 거라고 믿고 대출을 마구 해주는 '부분지급준비제도'와 비슷합니다.)
2. **뱅크런 발생 (Out Of Memory):** 그런데 어느 날, 프로그램들(특히 메모리 누수 버그가 있는 프로그램)이 약속과 달리 진짜로 메모리를 미친 듯이 끌어다 쓰기 시작합니다. 진짜 물리적 램(RAM)이 100% 꽉 차게 되면, 운영체제(리눅스) 자신이 숨 쉴 메모리조차 없어져서 컴퓨터 전체가 먹통이 될 위기에 처합니다. 이것이 바로 Out Of Memory(OOM) 상태입니다.
3. **시스템을 살리기 위한 암살자 등장 (OOM Killer):** 컴퓨터 전체가 멈추는 대형 사고(Kernel Panic)를 막기 위해, 리눅스 커널은 최후의 수단으로 **'OOM Killer'**라는 저격수를 기상시킵니다. OOM Killer는 현재 실행 중인 모든 프로세스를 쭉 훑어보고 '누구를 죽여야 시스템을 살릴 수 있을까?'를 계산합니다. 주로 **'메모리를 가장 뚱뚱하게 많이 먹고 있으면서, 죽여도 운영체제 시스템에는 타격이 적은 만만한 앱'**을 타겟으로 잡습니다.
4. **처형 (OOM Crash):** 타겟이 정해지면 OOM Killer는 경고도 없이 해당 프로세스의 목을 날려버립니다(`kill -9` 강제 종료 신호). 개발자 입장에서는 서버에서 잘 돌고 있던 프로그램이 아무런 에러 로그도 안 남기고 갑자기 픽 쓰러져서 죽어버리는 황당한 일을 겪게 되는데, 이를 OOM Crash라고 부르게 되었습니다.

**요약하자면:** OOM Crash는 단순한 에러가 아니라, **"메모리가 꽉 차서 컴퓨터 전체가 죽기 직전이라, 운영체제가 살기 위해 가장 뚱뚱한 프로그램(당신의 앱)을 골라 강제로 처형시킨 사건"**을 의미하는 무시무시한 용어입니다! 💀

## 🤔 번외: CPU 스파이크 말고 GPU 스파이크는 없나요?

당연히 있습니다! 오히려 게임 개발이나 그래픽 환경에서는 GPU 스파이크가 훨씬 잦고 치명적입니다. CPU 스파이크가 '게임의 두뇌(AI, 로직)' 과부하라면, GPU 스파이크는 **'게임의 눈(그래픽, 렌더링)' 과부하**입니다.

1. **파티클 대폭발:** 유저가 폭약통 100개에 수류탄을 던졌을 때, 수십만 개의 화염 파티클과 동적 광원(Lighting)을 순간적으로 계산하느라 GPU 사용률이 100%를 치며 프레임이 60FPS에서 5FPS로 떨어지는 렉 현상입니다.
2. **최적화 안 된 셰이더/초고화질 텍스처:** 8K 초고화질 텍스처와 수백만 가닥의 털 그림자를 가진 보스 몬스터가 화면에 잡히는 순간 그래픽 카드가 연산량을 감당하지 못하고 비명을 지르는 현상입니다.
3. **오버드로우(Overdraw):** 눈에 보이지도 않는 숲 맨 뒤쪽의 나무 100그루 나뭇잎까지 GPU가 전부 그려내느라 쓸데없는 연산 노동력을 낭비하여 발생하는 과부하입니다.

**Q. 그럼 왜 이번 과제에서는 GPU 스파이크를 다루지 않았나요?**
이번 과제의 타겟이 '일반 PC(클라이언트)'가 아니라 **'백엔드 서버'**이기 때문입니다. 
백엔드 서버는 화면을 렌더링할 필요 없이 데이터의 논리적인 계산만 수행하므로, 서버 컴퓨터에는 그래픽 카드(GPU)가 아예 장착되지 않는 경우가 대부분입니다. 따라서 서버 엔지니어의 세계에서는 오직 **CPU, 메모리(RAM), 스레드(Thread), 네트워크** 관리가 지상 최대의 핵심 과제가 됩니다.

## 🌟 [심층 분석 및 보너스 트러블슈팅]

### 1. 멀티플 버그(Multiple Bugs) 아키텍처 결함의 발견 🚨
> [!IMPORTANT]
> **충격적인 진실: OOM과 Deadlock의 기묘한 동거**
> 단순히 하나의 버그만 존재하는 것이 아니라, 타겟 애플리케이션은 **"256MB 이하 환경에서 프로세스를 강제 자결시키는 MemoryGuard 로직"**과 **"멀티스레드 환경에서 서로의 자원을 쥐고 영원히 대기하는 Deadlock 로직"**을 동시에 품고 있었습니다.
> - 따라서 데드락을 해결하기 위해 `Deadlock_After` 시나리오에서 `MULTI_THREAD_ENABLE=0`을 주더라도, 메모리 누수가 여전히 발생하여 500MB까지 꾸역꾸역 메모리가 차오르게 됩니다. 
> - 이 때문에 `Deadlock_After`의 메모리 설정값(512MB)이 `OOM_After`의 설정값과 동일하게 세팅되어 있어야만 테스트를 무사히 통과할 수 있었던 치밀하고 악랄한 다중 결함(Multiple Bugs) 시스템이었음이 실험을 통해 완벽히 증명되었습니다.

### 2. OS 모니터링의 맹점과 하이브리드 관제 아키텍처
> [!NOTE]
> **실무와 과제의 차이점 (의도적 설계)**
> 실제 실무 환경이었다면 OS 커널단 지표인 `top`과 `ps`를 신뢰하는 것이 표준 모범 사례(Best Practice)입니다. 그러나 본 과제의 타겟 앱은 의도적으로 연산과 휴식을 짧게 반복하는 **마이크로 버스트(Micro-sleep)** 기법을 사용하여 OS 폴링 도구들을 기만하도록 설계되었습니다.

- **Boot Spike의 함정과 오토 킬(Auto-Kill)**: 프로그램 기동 직후 `top` 명령어는 초기 구동 부하로 인해 일시적으로 `80.4%`를 보고했습니다. 만약 `top` 수치에만 의존해 오토 킬 로직을 구현했다면 정상 서비스조차 부팅 시점에 즉각 살해당했을 것입니다.
- **OS 기본 도구의 패배**: 주기를 0.5초로 극한까지 좁히더라도 타겟 앱의 휴식/연산 타이밍과 엇갈리면 영원히 `0%`를 출력하거나 관찰자 효과로 인해 `240%`라는 왜곡된 수치를 반환했습니다.
- **하이브리드 관제(Hybrid Monitoring)의 승리**: 결국, `top`이 요동치는 와중에도 관제 스크립트는 앱 내부 로그에서 `[CpuWorker] Current Load`를 파싱(`PARSING_CPU`)하여 부하의 팽창을 완벽히 추적했습니다. 프로세스 사망 시 단순 "PID Not Found"가 아니라 유언장(Log)으로부터 **`[CRITICAL] 프로세스 사망. 원인: [CpuWorker] CPU Threshold Violated! (54.13%)`** 이라는 정확한 사살 원인을 적출하는 데 성공했습니다.

### 3. 스케줄링 알고리즘 역추적 (Round-Robin)
정상 실행 상태(단일 스레드 모드)의 로그 타임스탬프와 작업 진행률을 분석한 결과, `Thread-A`, `Thread-B`, `Thread-C`가 정확히 40% 분량만큼 작업을 수행한 뒤 강제로 실행 권한을 뺏기고(Preempted) 다음 스레드에게 CPU를 넘겨주는 패턴을 보였습니다. 
- 만약 **선입선출(FCFS)**이었다면 A가 100% 끝날 때까지 CPU를 뺏기지 않았을 것입니다. 
- 만약 **선점형 우선순위(Priority)**였다면 번갈아가며 40%씩 공평하게 나누는 패턴이 붕괴되었을 것입니다. 
- 따라서 이 시스템은 **라운드 로빈(Round-Robin, RR)** 방식의 스케줄러로 구동됨을 완벽하게 추론할 수 있었습니다. 이는 응답 시간이 중요한 실시간 웹 서버에는 적합하나 연산을 한 번에 끝내야 하는 배치 서버에는 부적합한 아키텍처입니다.

### 4. 보안 및 컨테이너 아키텍처 강화
- **Secret Key 권한 탈취 방어**: `secret.key`가 읽기 전용(400) 권한을 갖도록 컨테이너 기동 직후 `chmod 400`을 명시적으로 강제하여 보안 규격을 충족했습니다.
- **UFW(방화벽) Active 정상화**: 컨테이너에 커널 네트워크 제어 권한(`NET_ADMIN`, `NET_RAW`)을 부여하여 `UFW Active` 상태를 성공적으로 연동시켰습니다.
- **영구 기록(Audit) 강화**: 타임아웃 판정 시 화면에만 출력되던 `[SUCCESS]` 로그를 `monitor.log` 최하단에 영구 저장(Append)하도록 파이프라인을 개선했습니다.
