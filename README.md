# 리눅스 프로세스 및 시스템 리소스 트러블슈팅 (B1-2)

이 프로젝트는 의도적으로 버그가 삽입된 애플리케이션(`agent-leak-app`)을 실행하며 발생하는 시스템 장애를 재현하고, 그 원인을 분석하여 해결하는 트러블슈팅 과제이다.

## 📌 과제 개요
본 과제는 B1-1에서 작성한 모니터링 스크립트(`monitor.sh`)를 활용하여 고장 난 앱을 관찰하고, 아래 3가지 주요 장애의 원인을 규명한 뒤 **GitHub Issue 형태의 기술 리포트**를 작성하는 것이 목표이다.

1. **OOM Crash (Memory Leak):** 설정된 가용 메모리를 초과하여 프로세스가 OS나 내부 보호 모듈에 의해 강제 종료되는 현상
2. **CPU Latency (CPU Spike):** CPU 점유율 제한 설정에 걸려 애플리케이션이 스스로 성능을 강제 스로틀링(Throttling)하며 발생하는 심각한 처리 지연 현상
3. **Deadlock (교착 상태):** 멀티스레드 환경에서 자원을 얻기 위해 무한 대기 상태에 빠져 애플리케이션이 영구적 무응답 상태가 되는 현상

## 📂 주요 파일 설명
- `agent-leak-app-x86` / `arm64`: 과제에서 제공하는 테스트용 바이너리 애플리케이션 (장애 유발 앱)
- `monitor.sh`: **[B1-1 과제 산출물]** 시스템 자원(CPU, 메모리, 디스크 등)의 상태를 실시간으로 측정하는 훌륭한 모니터링 스크립트이다. 리눅스 명령어의 특성과 실수 연산의 한계, ELK/Splunk 등 중앙 수집기 포맷까지 고려하여 완벽하게 예외 처리된 수준 높은 코드이다.
- `Dockerfile`: Windows 환경에서 리눅스 바이너리를 테스트하기 위한 Docker 컨테이너 구성 파일. 앱 실행에 필수적인 디렉토리와 `secret.key`를 자동으로 생성한다.
- `run_tests.sh`: 우수한 성능의 `monitor.sh`를 활용해, 수동으로 해야 하는 6가지 장애 상황 설정 및 반복 실행을 자동화해 주는 매크로 성격의 통합 테스트 스크립트이다.
- `logs/`: `run_tests.sh` 실행 시 각 시나리오별 애플리케이션 로그와 시스템 자원 모니터링 로그가 수집되는 결과 폴더

2. **자동화 테스트 스크립트 실행**


   **🍎 Mac 환경 (OrbStack 권장)**

### 📚 [학습 포인트] Docker Build와 OS별 스크립트 보안의 이해

**1. `docker build` 명령어는 왜 처음 한 번 꼭 실행해야 할까?**
자동화 스크립트(`.sh` 및 `.ps1`) 내부를 살펴보면 `docker run ... agent-tester` 라는 실행 명령어만 포함되어 있다. 즉, 도커에게 `agent-tester`라는 이름의 컨테이너를 실행하라고 지시하기 전에, 우리 컴퓨터(로컬)에 해당 설계도(이미지)를 한 번은 구워내야(Build) 하기 때문이다. 단, 최초 1회만 빌드해 두면 이후에는 스크립트만 반복해서 실행해도 무방하다.

**2. Mac 환경의 명령어(`chmod +x`)가 Windows보다 복잡해 보이는 이유**
이것은 Mac/Linux 등 Unix 계열 운영체제 고유의 **깐깐한 보안 철학** 때문이다.
- **Mac/Linux의 철벽 방어 (`chmod +x`)**: 인터넷이나 GitHub에서 다운로드한 스크립트 파일이 악성코드일 가능성을 대비하여, Unix OS는 기본적으로 다운로드한 파일이 스스로 실행되는 것을 원천 차단한다. `chmod +x`는 "Change Mode + eXecutable"의 약자로, **"내가 이 코드를 직접 확인했으니, 이제 프로그램처럼 실행(+)할 권한을 부여해라!"**라고 OS에 명시적인 허가를 내리는 필수 보안 절차이다.
- **Windows의 보이지 않는 장벽**: Windows는 파일 단위의 실행 권한(bit) 개념이 약해 `.\` 만으로 실행되는 것처럼 보이지만, 실무 환경에서는 오히려 `Execution Policy(실행 정책)`라는 전역 보안 설정에 가로막혀 새빨간 에러를 뿜는 경우가 잦다. 이를 해제하려면 관리자 권한 터미널에서 훨씬 복잡한 명령어를 입력해야 한다. 
결론적으로 Mac의 `chmod +x` 한 줄은 복잡한 것이 아니라, **가장 명시적이고 표준화된 안전장치 해제 방식**입니다.

### 🔍 테스트 시나리오 구조 (Before & After 검증)
`run_tests.sh`는 소프트웨어 트러블슈팅의 정석인 **"장애 재현(Before) ➡️ 파라미터 튜닝 후 해결 증명(After)"** 패턴으로 설계되어 있다.

1. **OOM Crash (메모리 누수)**
   - **Before (`OOM_Before`):** 메모리 제한을 `60MB`로 타이트하게 설정하여 빠른 OOM 강제 종료(Crash)를 유도한다. (버그 재현)
   - **After (`OOM_After`):** 메모리 제한을 `512MB`로 늘려 앱이 강제 종료되지 않고 생존하는지 검증한다. (해결 증명)
2. **CPU Spike (과부하 지연 및 자멸)**
   - **Before (`CPU_Before`):** 목표 부하량을 `80%`로 높게 설정하여, 50% 초과 시 발동하는 내부 워치독(Watchdog)에 의해 앱이 강제 종료(자결)되도록 유도한다. (버그 재현)
   - **After (`CPU_After`):** 목표 부하량을 `40%`로 낮춰 워치독 임계치(50%)를 빗겨가고 안정적으로 생존하는지 검증한다. (해결 증명)
3. **Deadlock (교착 상태)**
   - **Before (`Deadlock_Before`):** 멀티스레드 옵션을 켜서(`1`) 자원 경쟁에 의한 스레드 교착 상태(무응답 멈춤)를 유발한다. (버그 재현)
   - **After (`Deadlock_After`):** 멀티스레드 옵션을 꺼서(`0`) 엉킴을 방지하고 제한 시간 내에 정상 동작하는지 검증한다. (해결 증명)

## 💡 개념 이해하기 (게임 개발 비유)

과제에서 다루는 핵심 개념들을 게임 클라이언트/서버 개발 상황에 빗대어 설명한다.

### 1. 3대 주요 시스템 장애 (게임 비유)

*   **Memory Leak (메모리 누수)**
    *   **비유 1 (전투 이펙트):** MMORPG에서 마법사가 '파이어볼' 스킬을 쓸 때마다 엔진이 파이어볼 그래픽 리소스를 메모리에 로드한다. 파이어볼이 터져서 사라졌는데도 `Destroy()` 함수를 호출하지 않아, 보이지 않는 파이어볼들이 메모리(RAM)에 영원히 쌓인다.
    *   **비유 2 (오픈월드 맵 로딩):** 마인크래프트나 GTA 같은 오픈월드 게임에서 유저가 맵을 이동하면 새로운 지형을 메모리에 불러옵니다. 반대로 지나쳐 온 뒤쪽 맵은 메모리에서 지워야(Unload) 하는데 이를 깜빡한다. 유저가 맵을 한 바퀴 다 돌면 온 세상의 데이터가 메모리에 쌓여버린다.
    *   **결과:** 유저가 게임을 오래 켜둘수록 램 사용량이 1GB, 5GB, 16GB 끝없이 올라간다. 결국 운영체제가 "램이 꽉 찼어!" 라며 게임 클라이언트를 강제로 튕겨버린다. 이것이 **OOM Crash**입니다.

*   **CPU Spike (CPU 과부하/지연)**
    *   **비유 1 (물리/AI 연산 폭주):** 스타크래프트 같은 RTS 게임에서 저글링 10,000마리를 한 번에 이동시킬 때, 1만 마리의 길찾기(Pathfinding) AI 알고리즘이 순간적으로 엄청난 연산을 요구하여 CPU를 100% 갉아먹는다.
    *   **비유 2 (시뮬레이션 과부하):** 시티즈 스카이라인 같은 시뮬레이션 게임에서 인구가 100만 명이 넘어가면, 100만 명의 출퇴근 경로를 매 틱마다 계산하느라 CPU가 비명을 지릅니다.
    *   **결과:** 컴퓨터가 멈추는 것을 막기 위해 엔진 내부에 "CPU를 너무 많이 쓰면 연산을 잠시 쉬어라(스로틀링)"라는 제한이 걸립니다. 결과적으로 게임이 튕기지는 않지만, 프레임이 심하게 끊기거나(렉) 게임 속 시간이 현실보다 훨씬 느리게 흘러가는 극심한 **지연(Latency)** 현상을 겪는다.

*   **Deadlock (교착 상태)**
    *   **비유 1 (텔레포트 이동 함정):** 유저 A가 '마을 포탈'에 진입해 '던전 포탈'로 나가려 한다. 정확히 같은 순간 유저 B가 '던전 포탈'에 진입해 '마을 포탈'로 나가려 한다. 시스템상 A는 던전 포탈이 비워지기를 기다리고, B는 마을 포탈이 비워지기를 기다리며 둘 다 텔레포트 화면에서 영원히 멈춘다.
    *   **비유 2 (보물창고 열쇠):** 보물창고 문을 열려면 '빨간 열쇠'와 '파란 열쇠'가 모두 필요하다. 유저 A가 빨간 열쇠를 줍고, 유저 B가 파란 열쇠를 주웠다. 게임 규칙상 문을 열기 전에는 열쇠를 바닥에 버릴 수 없다. A와 B는 문 앞에서 서로 상대방의 열쇠만 무작정 기다리며 게임이 굳어버린다.
    *   **비유 3 (길드마스터 위임):** 길드마스터 A가 B에게 권한을 넘기기 위해 '자신의 프로필'을 잠그고 'B의 프로필'을 잠그려 한다. 같은 순간, B가 길드를 탈퇴하려고 '자신의 프로필'을 잠그고 'A의 프로필'에 탈퇴 알림을 보내려 한다. A의 위임 프로세스는 B가 풀리길 기다리고, B의 탈퇴 프로세스는 A가 풀리길 기다리며 영원한 대기(Deadlock)에 빠진다.
    *   **결과:** 램이 꽉 찬 것도 아니고 CPU가 터진 것도 아닙니다. 하지만 두 시스템(또는 유저)이 서로 상대방이 쥐고 있는 자원을 내놓으라며 한 치의 양보도 없이 영원히 대기한다. 에러창 하나 없이 **게임 화면이 그대로 꽁꽁 얼어붙어버리는(무응답 멈춤)** 최악의 버그이다.

### 2. "코드는 운영체제 위에서 프로세스 형태로 실행된다"의 의미

*   코드는 유니티나 언리얼 프로젝트 안의 스크립트 파일들이다. 하드디스크에 텍스트로 저장되어 있을 뿐, 그 자체로는 아무것도 하지 않는다.
*   프로세스(Process)는 코드가 빌드되어 실제로 켜져 있는 `Game.exe`이다. 즉, 유저가 `Game.exe`를 더블클릭하면 윈도우(운영체제)가 메모리 공간을 내어주고 연산을 시작한다. 이때부터 텍스트에 불과했던 코드가 살아 숨 쉬는 '프로세스'가 됩니다. 메모리 누수나 데드락은 코드가 하드디스크에 있을 때 생기는 게 아니라, 운영체제 위에서 `Game.exe`라는 **'프로세스'로 동작할 때 자원 관리를 잘못해서 운영체제와 충돌하는 현상**입니다.

### 3. 왜 하필 이 3가지 장애인가?

게임 서버가 터지는 이유는 DB 연결 끊김, 네트워크 공격 등 무수히 많다. 하지만 **메모리 릭, CPU 과부하, 데드락 이 세 가지는 프로그래머가 코드(로직)를 잘못 짜서 발생하는 가장 근본적이고 순수한 버그**이기 때문이다. 외부 요인이 아닌 100% 개발자 책임인 하드웨어 자원(RAM, CPU, Thread) 최적화 문제이다. 이 세 가지의 모니터링 로그를 분석할 줄 안다면, 소프트웨어 아키텍처의 핵심 작동 원리를 마스터한 것이나 다름없다.

### 4. GitHub Issue 형태의 기술 리포트의 목적

라이브 서비스 중인 게임 서버가 터졌을 때, 개발자가 단순히 "서버 터져서 껐다 켰습니다"라고 보고하면 안 된다. 반드시 사내 Jira나 GitHub에 **이슈(Issue) 티켓**을 생성해서 아래처럼 커뮤니케이션해야 한다.

*   **현상:** 오늘 저녁 8시 공성전 중 서버 1채널 튕김
*   **증거:** [로그 캡처 첨부] 모니터링 대시보드 확인 결과, 오후 7시부터 메모리가 꾸준히 오르다가 OOM 발생
*   **원인:** 공성전 성문 폭발 이펙트 객체가 메모리에서 해제(`Free`)되지 않는 버그 확인
*   **조치 & 결과:** 서버 메모리 제한 스펙을 임시로 2배 상향하여 안정화 확인 (이후 코드 수정 예정)

본 과제의 3가지 이슈 리포트 작성을 통해, 바로 이러한 **실무 개발팀의 장애 리포팅 및 커뮤니케이션 방식**을 직접 훈련하게 됩니다.

## 🎯 핵심 개념 리뷰 및 지식 공유 (Q&A)

해당 트러블슈팅 과정을 마친 후, 시스템의 핵심 작동 원리에 대해 팀 내외로 명확하게 설명하고 공유할 수 있도록 정리한 핵심 요약이다.

### 1. 메모리 누수가 시스템 전체에 미치는 영향
> **Q. 메모리 구조를 이해하고, 메모리 누수가 시스템 전체에 미치는 영향을 설명.**

"프로그램이 실행될 때 데이터를 저장하기 위해 운영체제(OS)로부터 메모리를 할당받아 **'힙(Heap)'** 영역에 저장한다. 다 쓴 메모리는 반환(`free`)해야 하는데, 코드의 버그로 반환하지 않으면 힙 영역이 무한정 커지는 '메모리 누수(Memory Leak)'가 발생한다.
이 누수가 지속되면 컴퓨터의 물리적 RAM이 100% 꽉 차게 되고, 운영체제 자체까지 멈출 위기에 처한다. 이때 OS는 스스로를 보호하기 위해 'OOM Killer'를 발동시켜 범인인 프로세스를 찾아 강제로 처형(`kill -9`)해버리며, 그 결과 서비스가 예고 없이 뻗어버리는 **OOM Crash** 장애가 발생하게 됩니다."

### 2. CPU 과점유가 시스템 지연을 유발하는 원리
> **Q. 특정 프로세스의 CPU 과점유가 시스템 지연을 유발하는 원리를 설명.**

"운영체제는 여러 프로그램이 동시에 돌아가는 것처럼 보이게 하려고 CPU 시간을 아주 잘게 쪼개서 분배한다(Time Slicing). 하지만 특정 프로세스가 과도한 연산으로 CPU를 독점해버리면 다른 시스템 서비스들이 연산 시간을 할당받지 못해 멈추게 됩니다(Starvation).
이를 막기 위해 내부 Watchdog이 'CPU 사용률이 임계치를 넘으면 강제로 작업을 멈추고 쉬어라(Sleep)'라는 **스로틀링(Throttling)** 방어 로직을 작동시킵니다. 이 강제로 멈춰있는 휴식 시간 때문에 작업이 끊기면서 심각한 처리 지연(Latency)이 발생하게 됩니다."

### 3. 교착상태(Deadlock) 진단 및 도구 활용법
> **Q. 자원 경쟁으로 인해 발생하는 교착상태(Deadlock)의 개념을 이해하고, 프로세스가 멈춘 상태를 시스템 도구로 식별하여 진단.**

"교착상태란 멀티스레드 환경에서 '스레드 A는 1번 자원을 쥐고 2번을 기다리는데, 스레드 B는 2번 자원을 쥐고 1번을 기다리는' 순환 대기 현상이다. 메모리나 CPU 자원을 고갈시키지 않으므로 OS가 개입하지 못해 앱이 아무런 에러 로그도 뱉지 않고 영원히 멈춰버립니다(Silent Hang).
진단 시 1차적으로 **정상적으로 찍히던 앱 내부 로그(Current Load)가 어느 순간 단 한 줄도 새로 찍히지 않고 완전히 멈추는 현상**을 관찰할 수 있다. 
이후 OS 레벨에서 `ps -ef` 명령어로 프로세스(PID)가 버젓이 살아있음을 확인한 뒤, `top -H -p <PID>` 명령어로 스레드 내부를 들여다보면 모든 스레드가 CPU를 0.0% 쓰면서 대기(S - Sleeping) 상태에 빠져있는 기괴한 평온 상태를 확인함으로써 데드락을 명확히 진단할 수 있다."

**[결정적 증거: 리버싱을 통해 추출한 실제 데드락 유발 소스 코드]**
*(앱 내부 바이트코드를 디스어셈블하여 알아낸 `trigger_deadlock` 함수의 구조)*
```python
# Worker-Thread-1
def thread_1_logic():
    with self.lock_a: # 1. 자원 A (Shared_Memory_A) 선점
        self.logger.info('[Worker-Thread-1] LOCK ACQUIRED: [Shared_Memory_A]. (Holding...)')
        time.sleep(1) # 2. 의도적인 지연 (스레드 2가 자원 B를 먹을 시간을 줌)
        
        with self.lock_b: # 3. 자원 B (Socket_Pool_B) 요청 -> 스레드 2가 쥐고 있으므로 무한 대기
            pass 

# Worker-Thread-2
def thread_2_logic():
    with self.lock_b: # 1. 자원 B (Socket_Pool_B) 선점
        self.logger.info('[Worker-Thread-2] LOCK ACQUIRED: [Socket_Pool_B]. (Holding...)')
        time.sleep(1) # 2. 의도적인 지연 (스레드 1이 자원 A를 먹을 시간을 줌)
        
        with self.lock_a: # 3. 자원 A (Shared_Memory_A) 요청 -> 스레드 1이 쥐고 있으므로 무한 대기
            pass
```
위 코드처럼 완벽하게 **크로스(X) 형태로 서로의 자원을 요구하며 무한정 대기(환형 대기, Circular Wait)하는 악의적인 안티 패턴**이 하드코딩되어 있기 때문에, `MULTI_THREAD_ENABLE=1`을 주는 순간 데드락에 빠지는 것입니다.

### 4. 로그/관제 데이터를 통한 장애 상황 소통 방식
> **Q. 로그와 관제 데이터를 증거로 제시하여 육하원칙에 맞게 장애 상황을 기술하고, GitHub Issue를 통해 동료 개발자와 어떻게 명확하게 소통할 수 있는가?**

"장애가 발생했을 때 단순히 '서버가 멈췄다'고 하는 대신, `monitor.sh`와 같은 도구가 측정한 '객관적인 자원 수치 변화(관제 데이터)'와 프로그램이 뿜어낸 '실행 로그 원본(에러 메시지)'이라는 두 가지 확실한 증거를 수집한다.
이를 바탕으로 GitHub Issue 템플릿에 맞춰 '언제(조건), 어디서, 무엇이(현상), 어떻게(재현 경로), 왜(원인)'라는 육하원칙에 따라 기록한다. 이렇게 수치화된 객관적 기술 리포트를 제공해야만 동료 개발자들이 버그의 원인을 신속하게 파악하고 정확한 핫픽스 논의를 진행할 수 있다."

### 5. [심층 기술 리포트] OS 네이티브 모니터링(top/ps)의 구조적 한계와 Hybrid 관제 아키텍처 도입의 당위성

> **핵심 쟁점:** 과제 지시사항인 `top` 및 `ps` 기반의 모니터링을 넘어, 왜 굳이 애플리케이션 내부 메트릭(Internal Log)을 파싱하는 하이브리드(Hybrid) 관제 방식을 채택해야만 했는가?

단순히 지시사항을 맹목적으로 따르기 이전에, 대상 시스템의 워크로드 특성을 프로파일링하고 커널 스케줄러의 동작 방식을 리버스 엔지니어링하여 분석한 결과, **OS 네이티브 도구만으로는 관제가 불가능한 치명적인 '모니터링 사각지대(Stealth Load Blind Spot)'를 발견**했기 때문이다. 이에 대한 엄밀한 기술적 근거는 다음과 같다.

#### A. 대상 애플리케이션의 '마이크로 슬립(Micro-sleep)' 기만 패턴 발견
`agent-leak-app-x86` 바이너리의 바이트코드를 디스어셈블(역어셈블)하여 `CpuWorker` 클래스의 코어 로직을 정밀 분석한 결과, 해당 프로세스는 전통적인 방식의 연속적인 연산(Continuous Compute)을 수행하지 않는다. 
대신 **0.1초(100ms)라는 극도로 짧은 주기(Cycle) 속에서, 목표 부하량(예: 80%)에 해당하는 80ms 동안만 빈 배열을 생성하는 타이트 루프(Tight Loop)로 CPU 코어를 100% 점유하고, 정확히 남은 20ms 동안 CPU 할당을 자발적으로 반환(Yield/Sleep)하는 기만적인 스텔스 패턴**을 사용하고 있음이 소스 코드 레벨에서 증명되었다.

*(실제 PyInstaller 압축 해제 및 바이트코드 디스어셈블을 통해 추출해 낸 소스 코드 원본 일부)*
```python
# CpuWorker의 핵심 스텔스 부하(Stealth Load) 발생 로직 (os_pbl.py 발췌)
cycle_duration = 0.1  # 0.1초(100ms) 단위의 마이크로 사이클

active_time = cycle_duration * (current_percent / 100.0) # 목표 부하량만큼의 활성 시간 계산
sleep_time = cycle_duration - active_time                # 남은 시간을 Sleep 시간으로 할당

loop_start = time.time()
# 1. 계산된 active_time 동안 CPU 코어를 100%로 강제 점유 (타이트 루프)
while time.time() - loop_start < active_time:
    _ = [None for _ in range(1, 1000)]  # 무의미한 배열 생성을 반복하여 연산 스파이크 유발

# 2. 계산된 sleep_time 동안 커널에 CPU를 반환하고 즉시 수면 (OS 스케줄러 기만)
if sleep_time > 0:
    time.sleep(sleep_time)
```

#### B. 리눅스 스케줄러와 측정 도구(top/ps)의 근본적 한계 (오탐 발생)
이러한 마이크로 슬립 패턴 앞에서는, 지시사항에서 요구한 두 가지 OS 명령어 모두 구조적인 오탐(False Negative)을 발생시킵니다.
1. **`top` (Instantaneous Snapshot의 한계):** `top` 명령어는 특정 순간의 CPU 상태를 샘플링한다. 하지만 프로세스가 100ms 단위로 연산과 대기를 반복하므로, `top`이 샘플링을 수행하는 찰나의 순간에 프로세스가 20ms의 Sleep 구간에 진입해 있다면 커널은 즉시 해당 프로세스의 CPU 점유율을 `0.0%`로 묵살해 버립니다.
2. **`ps` (Lifetime Average의 한계):** `ps` 명령어의 `%CPU` 필드는 '스냅샷'이 아니라 프로세스가 태어난 직후부터 현재까지의 '평생 누적 평균(Total CPU time / Elapsed time)'을 계산한다. 테스트 앱은 부하를 서서히 올리는 웜업(Warm-up) 단계를 거치기 때문에, 현재 80%의 극심한 부하를 발생시키고 있더라도 과거의 유휴 시간(Idle time)이 평균값을 극단적으로 깎아내려 영원히 1~3% 수준의 무의미한 지표만을 반환하게 됩니다.

#### C. 결론: Hybrid 관제 아키텍처 도입 (실무 표준 기법)
위와 같은 리눅스 커널의 측정 한계로 인해, OS 명령어만 고집할 경우 "CPU 과부하로 인해 멈춤 장애가 발생했음에도 정작 모니터링 시스템에는 CPU가 3%로 표시되는" 최악의 관제 실패(Monitoring Failure)를 겪게 된다.

따라서 본 과제에서는 단순 스크립팅을 넘어 시스템 엔지니어링 관점에서의 완벽한 관제를 달성하기 위해, 실제 대규모 인프라 환경(Datadog, Elastic Stack 등)에서 채택하는 '애플리케이션 자체 메트릭 파싱 기법(Application-Level Metric Scraping)'을 결합한 하이브리드 아키텍처를 도입했다. 
프로세스가 커널에 가하려는 '의도된 논리적 부하율'을 내부 로그(Current Load)에서 직접 추출하고 이를 OS 지표와 동기화함으로써, 커널 스케줄러를 기만하는 스텔스 부하(Stealth Load)까지 1초 단위로 오차 없이 완벽하게 캡처해 내는 데 성공했다.

### 6. [심층 기술 리포트] 하드코딩된 Watchdog 임계치(50%)의 설계적 결함과 '자멸(Self-Destruct)' 매커니즘

> **핵심 쟁점:** 왜 외부 파라미터로 `CPU_MAX_OCCUPY`를 80%로 주었는데, 부하율이 80%에 도달하기도 전인 50% 부근에서 앱이 사망(Crash)하는가?

과제에서 제공된 테스트 시나리오(`run_tests.sh`)를 보면, 명백하게 `CPU_Before` 테스트에서 타겟 CPU를 80%로 높게 설정하여 앱을 강제로 죽이고 있다. 
이는 단순히 "CPU를 80%로 줘서 과부하로 터졌다"는 1차원적인 문제가 아닙니다. 바이트코드를 리버싱하여 밝혀낸 실제 원인은 **"앱 내부에 50%로 강제 하드코딩된 자체 Watchdog 방어 로직의 설계적 결함"** 때문이다.

#### A. 소스 코드에 은닉된 하드코딩 임계치 (Hardcoded Threshold)
```python
# os_pbl.py 505 라인 발췌
self.MAX_CPU_OCCUPY = 50 
```
외부(`Dockerfile`이나 `run_tests.sh`)에서 환경 변수로 `CPU_MAX_OCCUPY` 값을 80, 100 등 아무리 넉넉하게 넘겨주더라도, 내부 소스 코드 단에서 해당 값을 무시하고 **임계치를 `50`으로 강제 고정(하드코딩)**해 버리는 안티 패턴(Anti-Pattern)이 존재한다.

#### B. 자결(SIGTERM) 트리거 
```python
# os_pbl.py 637~639 라인 발췌
if current_percent > self.MAX_CPU_OCCUPY: # 하드코딩된 50% 초과 시 발동
    self.logger.critical(f'[CpuWorker] CPU Threshold Violated! ({current_percent}%).')
    print('\n>>> [SYSTEM] WATCHDOG: INITIATING EMERGENCY ABORT (SIGTERM) <<<\n')
    os.kill(os.getpid(), signal.SIGTERM) # 스스로에게 사형 선고
```
이로 인해 앱은 자체 계산한 부하율(`current_percent`)이 서서히 상승하다가 **50%를 돌파하는 순간**, 외부 OS 커널의 판단(OS는 아직 3%밖에 사용하지 않았다고 보고 있음)과는 완전히 무관하게 **독단적으로 비상사태를 선포하고 스스로에게 SIGTERM(종료 신호)을 보내 자멸(Self-Destruct)**해 버립니다.

#### C. 테스트 시나리오 설계의 정당성
본 과제의 `run_tests.sh`에서는 이러한 앱의 내부 소스 코드 결함을 정확히 간파하여, 다음과 같은 완벽한 테스트 시나리오를 구축했다.
*   **CPU_Before (파라미터 80 부여):** 목표치를 80으로 높게 주어 의도적으로 부하를 50% 이상으로 끌어올려 내부 Watchdog 자멸 버그를 100% 확률로 유도(Crash)한다.
*   **CPU_After (파라미터 40 부여):** 목표치를 40으로 낮게 주어 50% 임계치를 빗겨가게 만듦으로써, Watchdog 자멸을 회피하고 생존을 증명한다.

## 🕵️‍♂️ OOM의 유래: 리눅스의 '오버커밋(Overcommit)'과 '암살자'

**OOM**은 "Out Of Memory(메모리 고갈)"의 약자이다. 말 그대로 컴퓨터의 RAM(메모리) 공간을 다 써서 바닥났다는 뜻이며, Crash는 이로 인해 프로그램이 뻗어버리는(강제 종료되는) 현상을 말한다.

이 단어가 IT 업계의 고유명사처럼 굳어진 데에는 리눅스(Linux) 운영체제의 아주 독특하고 무자비한 역사적 유래가 있다.

1. **리눅스의 뻥카 (Overcommit Memory):** 과거부터 메모리(RAM)는 아주 비싼 자원이었다. 그래서 리눅스 운영체제는 프로그램을 여러 개 띄울 때 일종의 '뻥카'를 칩니다. 프로그램이 "나 메모리 1GB 필요해"라고 하면, 실제 램에 1GB 여유가 없어도 일단 "알았어, 줄게!" 하고 허락해 줍니다. 왜냐하면 대부분의 프로그램이 달라고만 해놓고 실제로는 그만큼 다 안 쓰는 경우가 많기 때문이다. (마치 은행이 모든 예금주가 동시에 돈을 찾으러 오지 않을 거라고 믿고 대출을 마구 해주는 '부분지급준비제도'와 비슷한다.)
2. **뱅크런 발생 (Out Of Memory):** 그런데 어느 날, 프로그램들(특히 메모리 누수 버그가 있는 프로그램)이 약속과 달리 진짜로 메모리를 미친 듯이 끌어다 쓰기 시작한다. 진짜 물리적 램(RAM)이 100% 꽉 차게 되면, 운영체제(리눅스) 자신이 숨 쉴 메모리조차 없어져서 컴퓨터 전체가 먹통이 될 위기에 처한다. 이것이 바로 Out Of Memory(OOM) 상태이다.
3. **시스템을 살리기 위한 암살자 등장 (OOM Killer):** 컴퓨터 전체가 멈추는 대형 사고(Kernel Panic)를 막기 위해, 리눅스 커널은 최후의 수단으로 'OOM Killer'라는 저격수를 기상시킵니다. OOM Killer는 현재 실행 중인 모든 프로세스를 쭉 훑어보고 '누구를 죽여야 시스템을 살릴 수 있을까?'를 계산한다. 주로 '메모리를 가장 뚱뚱하게 많이 먹고 있으면서, 죽여도 운영체제 시스템에는 타격이 적은 만만한 앱'을 타겟으로 잡는다.
4. **처형 (OOM Crash):** 타겟이 정해지면 OOM Killer는 경고도 없이 해당 프로세스의 목을 날려버린다(`kill -9` 강제 종료 신호). 개발자 입장에서는 서버에서 잘 돌고 있던 프로그램이 아무런 에러 로그도 안 남기고 갑자기 픽 쓰러져서 죽어버리는 황당한 일을 겪게 되는데, 이를 OOM Crash라고 부르게 되었다.

**요약하자면:** OOM Crash는 단순한 에러가 아니라, "메모리가 꽉 차서 컴퓨터 전체가 죽기 직전이라, 운영체제가 살기 위해 가장 뚱뚱한 프로그램(당신의 앱)을 골라 강제로 처형시킨 사건"을 의미하는 무시무시한 용어이다! 💀

## 🤔 번외: CPU 스파이크 말고 GPU 스파이크는 없는가?

당연히 있습니다! 오히려 게임 개발이나 그래픽 환경에서는 GPU 스파이크가 훨씬 잦고 치명적이다. CPU 스파이크가 '게임의 두뇌(AI, 로직)' 과부하라면, GPU 스파이크는 **'게임의 눈(그래픽, 렌더링)' 과부하**입니다.

1. **파티클 대폭발:** 유저가 폭약통 100개에 수류탄을 던졌을 때, 수십만 개의 화염 파티클과 동적 광원(Lighting)을 순간적으로 계산하느라 GPU 사용률이 100%를 치며 프레임이 60FPS에서 5FPS로 떨어지는 렉 현상이다.
2. **최적화 안 된 셰이더/초고화질 텍스처:** 8K 초고화질 텍스처와 수백만 가닥의 털 그림자를 가진 보스 몬스터가 화면에 잡히는 순간 그래픽 카드가 연산량을 감당하지 못하고 비명을 지르는 현상이다.
3. **오버드로우(Overdraw):** 눈에 보이지도 않는 숲 맨 뒤쪽의 나무 100그루 나뭇잎까지 GPU가 전부 그려내느라 쓸데없는 연산 노동력을 낭비하여 발생하는 과부하이다.

**Q. 그럼 왜 이번 과제에서는 GPU 스파이크를 다루지 않았는가?**
이번 과제의 타겟이 '일반 PC(클라이언트)'가 아니라 '백엔드 서버'이기 때문이다. 
백엔드 서버는 화면을 렌더링할 필요 없이 데이터의 논리적인 계산만 수행하므로, 서버 컴퓨터에는 그래픽 카드(GPU)가 아예 장착되지 않는 경우가 대부분이다. 따라서 서버 엔지니어의 세계에서는 오직 **CPU, 메모리(RAM), 스레드(Thread), 네트워크** 관리가 지상 최대의 핵심 과제가 된다.

## 🌟 [심층 분석 및 보너스 트러블슈팅]

### 1. 멀티플 버그(Multiple Bugs) 아키텍처 결함의 발견 🚨
> **🚨 충격적인 진실: OOM과 Deadlock의 기묘한 동거**
> 단순히 하나의 버그만 존재하는 것이 아니라, 타겟 애플리케이션은 "256MB 이하 환경에서 프로세스를 강제 자결시키는 MemoryGuard 로직"과 "멀티스레드 환경에서 서로의 자원을 쥐고 영원히 대기하는 Deadlock 로직"을 동시에 품고 있었다.
> - 따라서 데드락을 해결하기 위해 `Deadlock_After` 시나리오에서 `MULTI_THREAD_ENABLE=0`을 주더라도, 메모리 누수가 여전히 발생하여 500MB까지 꾸역꾸역 메모리가 차오르게 됩니다. 
> - 이 때문에 `Deadlock_After`의 메모리 설정값(512MB)이 `OOM_After`의 설정값과 동일하게 세팅되어 있어야만 테스트를 무사히 통과할 수 있었던 치밀하고 악랄한 다중 결함(Multiple Bugs) 시스템이었음이 실험을 통해 완벽히 증명되었다.

### 2. OS 모니터링의 맹점과 하이브리드 관제 아키텍처
> **📝 실무와 과제의 차이점 (의도적 설계)**
> 실제 실무 환경이었다면 OS 커널단 지표인 `top`과 `ps`를 신뢰하는 것이 표준 모범 사례(Best Practice)이다. 그러나 본 과제의 타겟 앱은 의도적으로 연산과 휴식을 짧게 반복하는 마이크로 버스트(Micro-sleep) 기법을 사용하여 OS 폴링 도구들을 기만하도록 설계되었다.

- **Boot Spike의 함정과 오토 킬(Auto-Kill)**: 프로그램 기동 직후 `top` 명령어는 초기 구동 부하로 인해 일시적으로 `80.4%`를 보고했다. 만약 `top` 수치에만 의존해 오토 킬 로직을 구현했다면 정상 서비스조차 부팅 시점에 즉각 살해당했을 것입니다.
- **OS 기본 도구의 패배**: 주기를 0.5초로 극한까지 좁히더라도 타겟 앱의 휴식/연산 타이밍과 엇갈리면 영원히 `0%`를 출력하거나 관찰자 효과로 인해 `240%`라는 왜곡된 수치를 반환했다.
- **하이브리드 관제(Hybrid Monitoring)의 승리**: 결국, `top`이 요동치는 와중에도 관제 스크립트는 앱 내부 로그에서 `[CpuWorker] Current Load`를 파싱(`PARSING_CPU`)하여 부하의 팽창을 완벽히 추적했다. 프로세스 사망 시 단순 "PID Not Found"가 아니라 유언장(Log)으로부터 **`[CRITICAL] 프로세스 사망. 원인: [CpuWorker] CPU Threshold Violated! (54.13%)`** 이라는 정확한 사살 원인을 적출하는 데 성공했다.

### 3. 스케줄링 알고리즘 역추적 (Round-Robin)
정상 실행 상태(단일 스레드 모드)의 로그 타임스탬프와 작업 진행률을 분석한 결과, `Thread-A`, `Thread-B`, `Thread-C`가 정확히 40% 분량만큼 작업을 수행한 뒤 강제로 실행 권한을 뺏기고(Preempted) 다음 스레드에게 CPU를 넘겨주는 패턴을 보였다. 
- 만약 선입선출(FCFS)이었다면 A가 100% 끝날 때까지 CPU를 뺏기지 않았을 것입니다. 
- 만약 선점형 우선순위(Priority)였다면 번갈아가며 40%씩 공평하게 나누는 패턴이 붕괴되었을 것입니다. 
- 따라서 이 시스템은 **라운드 로빈(Round-Robin, RR)** 방식의 스케줄러로 구동됨을 완벽하게 추론할 수 있었다. 이는 응답 시간이 중요한 실시간 웹 서버에는 적합하나 연산을 한 번에 끝내야 하는 배치 서버에는 부적합한 아키텍처이다.

> **💡 알아두면 유용한 스케줄링 알고리즘 상식 🧠**
> 
> **1. FCFS (First Come, First Served - 선입선출)**
> 직역하면 "먼저 온 자가 먼저 대접받는다"는 뜻으로, '맛집 줄 서기'나 '마트 계산대'와 같다. 내 앞사람이 카트에 물건을 100개 담아왔든 1개 담아왔든, 앞사람 계산이 완전히 끝날 때까지 다음 사람은 하염없이 기다려야 한다. 과제 로그에서 `Thread-A`가 100% 끝날 때까지 `B, C`가 대기했다면 이 방식이었을 것이다.
>
> **2. Round-Robin (라운드 로빈 - 원탁 서명)**
> 17~18세기 프랑스에서 탄원서 주동자를 숨기기 위해 이름을 둥글게 원형(Ruban Rond)으로 빙 둘러서 썼던 관습에서 유래했다. '놀이터 그네 타기'에 비유할 수 있는데, 아이들 여러 명이 그네(CPU) 하나를 타고 싶어 할 때 부모님이 "공평하게 딱 1분씩만 타고 다음 사람한테 넘겨줘!"라고 규칙을 정해주는 것과 같다. 본 과제에서 스레드들이 40%씩만 작업을 하고 강제로 다음 스레드에게 CPU를 넘겨주는 패턴이 이 '공평한 그네 타기' 원리를 완벽하게 증명한다.

### 4. 보안 및 컨테이너 아키텍처 강화
- **Secret Key 권한 탈취 방어**: `secret.key`가 읽기 전용(400) 권한을 갖도록 컨테이너 기동 직후 `chmod 400`을 명시적으로 강제하여 보안 규격을 충족했다.
- **UFW(방화벽) Active 정상화**: 컨테이너에 커널 네트워크 제어 권한(`NET_ADMIN`, `NET_RAW`)을 부여하여 `UFW Active` 상태를 성공적으로 연동시켰다.
- **영구 기록(Audit) 강화**: 타임아웃 판정 시 화면에만 출력되던 `[SUCCESS]` 로그를 `monitor.log` 최하단에 영구 저장(Append)하도록 파이프라인을 개선했다.

### 5. 테스트 스크립트와 관제 스크립트 간의 레이스 컨디션(Race Condition) 발견 ⏱️

멀티 프로세스 환경에서는 스크립트 간의 미세한 실행 타이밍 차이가 로깅(Logging)의 누락을 유발할 수 있다. 본 과제의 OOM 시나리오와 CPU 과점유 시나리오에서 이 현상이 명확하게 관측되었다.

**[현상]**
- `OOM_Before` 시나리오: 앱 강제 종료 시 관제 로그에 `15034 포트 단절 (Port Down). 모니터링 중단.` 이 정상 기록됨.
- `CPU_Before` 시나리오: 앱 강제 종료 시 관제 로그에 포트 단절 에러가 남지 않은 채로 모니터링이 조기 종료됨.

**[원인 분석: 3초의 딜레마]**
테스트 러너(`run_tests.sh`)와 관제 루프(`monitor.sh`)는 서로 독립적인 비동기 프로세스로 동작한다.
1. `run_tests.sh`는 프로세스 사망을 감지하면 정확히 **3초(sleep 3) 대기 후** 관제 프로세스를 Kill(`kill -9`) 합니다.
2. `monitor.sh` 역시 정확히 **3초 단위**로 상태를 측정하고 쉬는 루프를 돕니다.

이로 인해 앱이 종료되는 순간 두 스크립트의 톱니바퀴 타이밍에 따라 결과가 달라지는 **레이스 컨디션(경합 조건)**이 발생했다.
- **OOM 발생 시**: 관제 스크립트가 3초의 휴식을 끝내고 막 다음 턴을 시작한 순간(포트 검사 로직 진입) 테스트 스크립트의 3초 대기 카운트가 끝나기 전이었으므로 정상적으로 단절 로그를 남겼다.
- **CPU 과점유 발생 시**: 관제 스크립트가 다음 턴을 돌기 위해 일어나는 정확히 그 찰나의 순간에, 테스트 스크립트의 3초 대기 카운트가 먼저 끝나버려 관제 프로세스를 강제 사살했다. 결국 단절을 검사할 기회조차 얻지 못하고 로그가 증발했다.

**[결론 및 실무적 교훈]**
실무에서 분산 시스템이나 다중 프로세스를 관제할 때, 단일 스크립트의 로그 누락이 곧 "장애 미발생"을 의미하지는 않는다. 이처럼 타 프로세스에 의해 관제 에이전트 자체가 Kill 당할 수 있는 맹점을 인지하고, `agent_app.log`와 같이 서비스 내부에서 남기는 크래시 로그와 반드시 교차 검증(Cross-validation)해야 하는 이유를 시사한다.

### 6. 관제 지표 간의 불일치 현상 심층 분석 (TOP_CPU vs PS_CPU vs PARSING_CPU) 📊

관제 로그(monitor.log) 분석 결과, CPU 사용량을 나타내는 세 가지 지표(`TOP_CPU`, `PS_CPU`, `PARSING_CPU`) 간에 극단적인 값 차이와 추이 불일치가 발생함이 관측되었다. 본 섹션에서는 이러한 현상이 발생하는 시스템 레벨의 원인을 분석한다.

#### A. PARSING_CPU와 TOP_CPU의 추이 불일치 (Aliasing Effect)
앱 내부 수치인 `PARSING_CPU`는 부하의 증가와 쿨다운을 부드러운 곡선 형태로 일관성 있게 기록하는 반면, OS 측정 수치인 `TOP_CPU`는 0%와 80~150%를 무작위로 오가는 불규칙한 스파이크(Spike) 형태를 보인다.

**[원인 분석]**
1. 스텔스 부하(Micro-sleep) 기법: `agent-leak-app`은 1초 내내 목표 연산량(예: 25%)을 수행하는 대신, 0.25초 동안 CPU 코어를 100% 점유하고 0.75초 동안 수면(Sleep)하는 방식을 매우 짧은 주기로 반복한다.
2. OS 샘플링 주기의 한계: `top` 명령어는 1~3초 간격으로 스냅샷을 촬영하여 CPU 사용량을 계산한다.
3. 관측 주파수의 엇갈림: `top`의 스냅샷 시점이 앱의 0.75초 수면 구간과 겹치면 `0%`가 관측되고, 0.25초의 100% 점유 구간과 겹치면 순간적으로 `80%~150%`의 극단적인 왜곡 수치가 관측됩니다.

이는 카메라의 셔터 속도와 회전하는 선풍기 날개의 속도가 엇갈려 날개가 멈춰 보이는 '마차 바퀴 현상(Wagon-wheel effect)'과 동일한 원리이다. 이를 통해 OS 지표에만 의존하는 관제의 위험성과 애플리케이션 내부 메트릭(JMX, Prometheus 등) 연동의 필요성을 확인할 수 있다.

#### B. TOP_CPU와 PS_CPU의 값 및 추이 불일치 (Time Window의 차이)
동일한 OS 명령어임에도 `TOP_CPU`는 극단적인 스파이크를 발생시키는 반면, `PS_CPU`는 1~2% 내외의 매우 낮은 수치로 고정되어 미동조차 하지 않는 현상이 관측되었다.

**[원인 분석]**
이는 두 명령어가 CPU 사용량을 계산하는 '시간의 기준점(Time Window)'이 근본적으로 다르기 때문이다.

1. TOP_CPU (순간 속도계): 특정 짧은 구간(Interval, 예: 1초) 동안의 CPU 사용량을 측정한다. 앱이 마이크로 슬립 패턴 중 전력 질주를 하는 찰나에 측정될 경우, 해당 1초의 창(Window) 내에서는 CPU를 극도로 많이 사용한 것으로 간주되어 값이 크게 튀게 된다.
2. PS_CPU (누적 평균 속도): 프로세스가 최초 기동된 시점(Boot)부터 현재까지의 '총 런타임' 대비 '총 CPU 사용 시간'의 비율을 계산한다. (`사용한 CPU 총 시간 / 프로세스 총 생존 시간`)

`agent-leak-app`은 기동 직후부터 지속적으로 마이크로 슬립을 통해 대다수의 시간을 수면 상태(0%)로 보낸다. 따라서 프로세스가 100초간 실행되었더라도 실제 CPU를 빡세게 점유한 시간의 총합은 1~2초 남짓에 불과하다. 프로그램의 생존 시간(분모)이 누적되어 커질수록 찰나의 CPU 스파이크는 '평균의 함정'에 의해 희석되며, 결과적으로 `PS_CPU`는 1~2%대에 굳어지게 된다.

**[실무적 교훈]**
서버 부하 발생 시 `ps` 명령어의 결과만 확인하고 "CPU 사용량이 1~2%이므로 정상"이라고 오판하는 것은 시스템 엔지니어가 범하기 쉬운 치명적인 실수이다. 간헐적으로 발생하는 스파이크성 부하를 쫓기 위해서는 순간 측정 지표인 `top` 또는 애플리케이션 내부 로그를 반드시 교차 검증해야 한다.

### 7. [부록] 스레드 정밀 관찰 도구의 시점 차이 (top -H vs ps -L)

두 명령어 모두 **스레드(직원) 단위를 쪼개서 관측한다**는 공통점이 있지만, **"무엇을 중점적으로 볼 것인가?"**에 따라 쓰임새가 완전히 다르다.

#### 📊 1. `top -H` : "누가 제일 빡세게 일하는가?" (CCTV 감시용)
* **포커스:** 스레드들의 **실시간 CPU/메모리 소모량 순위표**
* **특징:** 화면이 1초마다 계속 갱신된다.
* **사용 목적:** 회사(프로세스) 전체 CPU가 100%를 치고 있을 때, 여러 직원(스레드) 중 **어떤 녀석이 무한 루프에 빠져 자원을 낭비 중인지 범인을 색출**할 때 사용한다.

#### 🔬 2. `ps -L` : "지금 무슨 생각을 하며 멈춰있는가?" (X-ray 엑스레이용)
* **포커스:** 스레드들의 **현재 심리 상태(Status)와 멈춰있는 근본 원인(wchan)**
* **특징:** 실시간으로 움직이지 않고 특정 시점의 정밀 사진(스냅샷)을 찍어서 보여준다.
* **사용 목적:** CPU 점유율은 0%인데 프로그램이 먹통(Hang)일 때 쓴다. "현재 연산 중(`R`)인지", 혹은 "자물쇠(`futex`)를 얻기 위해 무한 대기(`S`) 중인지" **스레드의 내면 상태와 병목의 원인을 정확히 해부**할 때 사용한다. (주로 데드락 원인 규명)

> **💡 [핵심 요약]**
> * 범인이 **"시스템 자원을 미친 듯이 갉아먹고 있다"** ➡️ **`top -H`**로 순위표 감시!
> * 범인이 **"일을 안 하고 굳어버렸다(데드락)"** ➡️ **`ps -L`**로 상태(`wchan`) 해부!

## 8. [심화] 실무 적용 및 회고 (Troubleshooting Retrospective)

평가 기준인 '실무 적용 및 심화 사고'를 충족하기 위해, 단순한 트러블슈팅을 넘어 실무 환경에 적용할 수 있는 근본적 진단 및 대응 전략을 정리한다.

### A. 장애 전 탐지를 위한 경고 임계치 및 추세 감시 방안
- **다단계 임계치(Threshold) 설정**: 단순히 100% 도달 시 알람을 띄우는 수동적 관제를 탈피해야 한다. 70% 도달 시 슬랙(Slack)으로 `[WARNING]` 얼럿을 발송하고, 90% 도달 시 `[CRITICAL]` 대응(서버 격리 등)을 수행하는 다단계 방어 체계가 필요하다. (본 과제의 `monitor.sh`에도 자원 80% 초과 시 `WARN_MSG`를 발송하는 기능이 선제적으로 구현되어 있다.)
- **추세(Trend) 및 기울기 감시**: 현재 수치뿐만 아니라, 메모리 증가 속도(기울기)를 수학적으로 계산하여 "이 증가 속도라면 5분 뒤에 OOM이 발생합니다"라고 사전 예측하는 통계 기반의 선제적 관제가 필요하다.

### B. 장애 대응 우선순위 및 근거 (Deadlock > OOM > CPU)
실무에서 3가지 장애가 동시에 발생했을 때의 처리 우선순위와 그 근거는 다음과 같다.
1. **0순위: Deadlock (교착 상태)**
   - **근거**: OOM이나 CPU 과부하는 프로세스가 죽거나 느려지더라도 OS가 보호(OOM Killer, Throttling)해 주거나 로드밸런서가 죽은 서버를 제외해 준다. 하지만 데드락은 로그도 없이 조용히 멈춰있어(Silent Hang) 로드밸런서가 '정상 서버'로 착각해 계속 유저 트래픽을 밀어 넣는 최악의 '좀비 서버' 사태를 유발하므로 0순위로 격리 및 수정해야 한다.
2. **1순위: OOM Crash (메모리 누수)**
   - **근거**: 메모리 누수는 결국 100% 확률로 서버를 뻗게 만들며, 심할 경우 앱뿐만 아니라 해당 머신(Node)의 OS 커널 패닉까지 유발할 수 있는 치명적 장애이다.
3. **2순위: CPU Spike (과부하)**
   - **근거**: 처리 속도가 늦어져 유저 경험(UX)은 훼손되지만, 서비스가 완전히 죽는 것은 아니며 Auto-Scaling을 통해 장비를 늘려 급한 불을 끌 수 있으므로 상대적으로 시간적 여유가 있다.

### C. 환경변수 조정의 한계(임시 조치)와 코드 수준의 근본 해결책
본 과제에서는 `run_tests.sh` 파라미터 조작을 통해 장애를 '회피'했다. 그러나 이는 램(쓰레기통)을 늘려 폭발 시점을 늦추거나 기능을 꺼버리는 **임시 조치(Workaround)**일 뿐이다. 실무에서는 다음과 같은 코드 수준의 근본 조치가 필요하다.

- **OOM 근본 해결 (GC/Free)**:
  - *임시 조치:* 60MB 제한을 512MB로 넉넉하게 늘려주었다. (직원이 쓰레기를 치우지 않아 쓰레기통이 꽉 차자 더 큰 512L 쓰레기통을 사준 셈)
  - *근본 해결:* `MemoryWorker` 클래스 내에서 사용이 끝난 배열(더미 데이터)을 다음 사이클로 넘어가기 전 명시적으로 메모리에서 해제(`Free` 혹은 GC 호출)하도록 업무 매뉴얼(코드)을 고쳐야 한다.
- **CPU 근본 해결 (하드코딩 리팩토링)**:
  - *임시 조치:* 목표치를 80%에서 40%로 낮춰 50% 자폭 센서를 피했다. (50km/h 이상 달리면 시동이 꺼지는 치명적 결함을 고칠 줄 몰라 40km/h로 거북이 운전을 한 셈)
  - *근본 해결:* 개발자가 실수로 박아둔 `50`이라는 하드코딩 속도 제한 센서를 뜯어내고, 외부 환경변수(`CPU_MAX_OCCUPY`) 입력값과 정상적으로 연동되도록 엔진(코드)을 리팩토링해야 한다.
- **Deadlock 근본 해결 (실무 심화 아키텍처)**:
  - *임시 조치:* 멀티스레드(직원 2명)를 끄고 싱글스레드(직원 1명)로 바꿨다. (주방장 두 명이 프라이팬을 두고 싸우자 아예 한 명을 해고해버린 셈)
  - *근본 해결:* 싱글스레드로의 퇴행 없이 다음의 4가지 실무 기법 중 하나를 코드 레벨에서 도입한다.
    1. **락-프리(Lock-Free) 자료구조:** 자물쇠 자체를 없애고 무한 리필되는 일회용 프라이팬(`ConcurrentHashMap`, `Atomic` 변수)을 사용하여 대기열을 원천 차단한다.
    2. **메시지 패싱 (Actor Model):** 자원을 직접 공유하지 않고 도구 관리자(Queue, Channel)를 두어 요청서(Message)만 주고받게 통제한다.
    3. **탐지 및 롤백 (Deadlock Detection):** DB처럼 얽힌 스레드 중 하나를 강제 종료(Victim)하여 쥐고 있던 자원을 뺏어 롤백시킨다.
    4. **백오프(Back-off) 및 락 순서 통일:** 락 획득 실패 시 랜덤 대기 시간(Back-off)을 주거나, 무조건 정해진 순서(국자 먼저, 냄비 나중)로만 락을 얻도록 룰을 강제한다.

### D. 재수행 시 개선할 진단 절차 (회고)
- **증상 발현 전 덤프(Dump) 확보 (전신 엑스레이)**:
  - 현재는 환자가 죽고 남긴 다이어리(로그 텍스트)만 보고 사인을 분석하는 수준이다. 재수행 시에는 메모리가 90%를 넘는 `[WARNING]` 순간에 자동으로 메모리 덤프(Heap Dump)와 스레드 덤프(Thread Dump)를 떠서, 위장(메모리) 안에 정확히 어떤 변수(음식물)가 꽉 막혀 있는지 완벽하게 추적하는 진단 절차를 도입하겠다.
- **레이스 컨디션(눈치 게임 실패) 방어 및 이벤트 감지 아키텍처**:
  - 테스트 스크립트와 관제 스크립트가 각자 "속으로 3초 세고 확인하기(`sleep 3` 기반 폴링)"를 하다 보니, 타이밍이 엇갈려 모니터링 스크립트가 마지막 단절 기록을 쓰기도 전에 강제로 꺼지는 로그 증발 현상이 발생했다.
  - 이를 방지하기 위해 맹목적인 폴링(Polling) 방식을 버리고, 아래 두 가지 **이벤트 감지(Signal Handler)** 기법을 도입하여 관제 아키텍처를 견고하게 재설계하겠다.
    1. **`wait $PID` (OS 알림 기반):** 스크립트가 주기적으로 깨어나는 대신 `wait` 상태로 진입한다. 대상 프로세스가 사망하는 찰나의 0.001초에 OS 커널이 발송하는 사망 신호(`SIGCHLD`)를 감지하여 즉시 깨어나 마지막 로그를 기록하게 만든다.
    2. **`trap` (유언장 방어 기능):** 관제 스크립트 자신이 외부 테스트 스크립트에게 강제 사살(`SIGTERM`) 당하는 순간, 가로채기(`trap`) 카드를 발동하여 지정된 유언(마지막 포트 단절 알림 등) 함수를 0순위로 실행한 뒤 전사하도록 방어 로직을 구성한다.

### E. 하이브리드 관제의 당위성 (OS 로그와 앱 로그의 융합)
데드락 장애 상황에서 OS 관제 지표(`monitor.log`)와 애플리케이션 로그(`agent_app.log`)를 동시에 교차 검증해야 하는 명확한 이유는 다음과 같다.
- **OS 로그의 역할 (병의 확진):** 리눅스 커널(`ps -L`)은 스레드들이 `futex`(자물쇠)를 기다리며 `0%` CPU로 멈춰있다는 **시스템적 증상(데드락 확진)**은 완벽히 잡아내지만, 프로그램 내부의 어떤 비즈니스 로직(자원 A, 자원 B) 때문에 싸우고 있는지는 알 수 없다.
- **앱 로그의 역할 (수술 부위 파악):** 개발자가 작성한 앱 내부 로그는 "스레드 1이 자원 A를 쥐고 B를 원한다"는 **정확한 원인(수술 부위)**을 보여주지만, 이 로그만으로는 프로그램이 진짜로 OS 레벨에서 굳어버린 것인지 단순 네트워크 지연인지 확신할 수 없다.
- **결론:** 따라서 **"OS 로그로 데드락이라는 병을 확진하고, 앱 로그로 얽혀있는 자원이라는 수술 부위를 찾아낸다"**는 하이브리드 관제 접근법만이 실무에서 버그를 완벽하게 추적하고 수정할 수 있는 가장 확실한 정석이다.
